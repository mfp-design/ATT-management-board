# 登録確認と回答修正のPoC

## 操作

- 初回の事業選択はSlackの確認ダイアログを表示し、「登録する」で送信、「戻る」で取消。
- 分類済みの投稿には通常文字の回答者表示と「回答を修正する」ボタンを置く。
- ボタンから事業9択と修正理由のモーダルを開く。「確認へ」では分類を保存しない。
- 変更前後の事業・理由を表示し、「修正を登録」で初めて保存する。キャンセル時は元の分類を保持する。
- 最初の分類履歴を残し、修正ごとの実操作ユーザーID・前後の事業・理由・時刻を別表へ追記する。
- セッションは操作ユーザー・ワークスペース・Slack view IDに紐づけ、30分で失効する。
- 古い画面、無効化・再割当カード、送信成否不明・送信中の投稿への修正は保存しない。
- 修正と履歴と表示更新キューを同じD1 batchで保存する。再送で修正履歴を増やさない。
- 送信処理はキューの取得権を確保してから分類を再読込し、直前の修正を古い表示で上書きしない。

## 配置と検証

`corrections.sql` を既存の検証D1へ適用済み。既存の原文・分類・最初の監査は保持。
コード版 `f0308004-9e13-4b51-a4a8-47b25260cff6` を100%配信。
変数・秘密情報を維持し、`POC_SLACK_SEND_ENABLED=false`、プレビューURL無効を確認した。
ユーザーが指定した既存の分類済み投稿1件へ修正ボタンを追加し、Slack API成功・outbox update=sentを確認。一時送信環境は停止済み。

`node --test tools/upsider-poc/*.test.mjs`：69件成功。
確認前に保存されないこと、二重送信、古い修正画面、別アカウント・別view・別チャンネル、
期限切れ、監査失敗時のロールバック、署名付きview_submissionの経路を含む。
実Slackのモーダル操作・応答時間・修正完了までの実地検証は未完了。

署名検証後の操作ユーザー、操作種別、対象、受付時刻、HTTP結果とresponse_actionを
`poc_interaction_receipts` に保存する。本文全文・秘密値・trigger_id・response_urlは残さない。
この記録は前回の回答者矛盾の再検証に使用する。過去の原因が解明された扱いにはしない。

## 配置時の是正

最初の配置で、Wranglerのno-bundle探索が一時フォルダ内の不要ファイルまで追加モジュールとして添付した。
直ちに専用フォルダのコードのみへ再配置し、不要な旧版
`524855f0-7af3-40f9-89d7-953cea62754b` はCloudflareの版削除APIで削除成功を確認した。
正常版の100%配信とプレビュー無効を確認済み。今後、entrypointを共有一時フォルダ直下に置いてno-bundleで配置しない。

## 制約

本人限定の認可は、後続の代理回答対応で変更した。最新状況は [代理回答の検証記録](responders-review.md) を参照。前回の回答者不一致は未解明のまま。
月次締め・役割別認可・理由付き代理回答の本番モデルはPoC外であり、本番運用開始を意味しない。
自動送信停止中は分類・修正結果をDBへ保存し、Slackの完了表示更新は手動実行する。
期限切れセッションや診断記録の保存期間・削除運用は本番化前に設定する。
