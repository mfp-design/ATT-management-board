## 1. 共通の集計契約

- 金額は税込日本円の整数。税抜・税率・消費税額は計算しない。通常明細の負数、1円未満、外貨は拒否し、マイナスは理由付き調整として区別する。合計も整数で保持し、表示用の万円表記を再計算の入力にしない。
- 日付境界は日本時間。利用日時等はJSTの日付へ変換してから対象期間を判定する。期間は開始日を含み、終了日の翌日00:00を含まない。APIでは開始inclusive／翌日exclusiveを推奨する。
- 売上・請求・入金・経費それぞれに、実績日（経費は利用日）、実績額、記録ID、元記録ID、事業、履歴を持つ。調整はどの種類の実績をいくら動かすかを明示する。例えば売上返品と現金返金は別記録で、片方から他方を自動推測しない。
- `period`（業務上の対象期間）、`as_of`（残高・案件状態の基準日）、`recorded_at`（システムが知った日時）、`close_version`（締め版）を区別する。取込日時を経費利用日に置換しない。
- 一つの集計に同じ記録IDを一度だけ含める。主担当・共同担当へのJOIN、兼務所属、再配信によって増やさない。外部イベントの識別方法は実通知PoCで確定し、このサンプルのID形式をSlack仕様とは扱わない。
- 未登録の予算は0円と区別し「未設定」を表示する。登録済みの部分合計を全期間の確定予算と見せない。前年同期データが不足する場合も比較値を0と捏造しない。
- 集計は状態／理由付き調整の履歴に基づく。案件・活動の誤登録取消は通常一覧から除外するが、財務実績や関連記録を連鎖削除しない。

## 2. 指標辞書

`ΣP`＝対象実績日が期間内にある有効実績と符号付き調整の合計。`Σ≤E`＝期間終了日までの累積。予定はこれらの実績に含めない。

権限：**業務**＝経営者と総務が業務権限の範囲で取得可能、**限定**＝予算・利益・人件費は経営者、および本番前または有効な一時許可のあるシステム担当だけ。支援コメントは経営者限定。本番開始後のシステム担当に自動的な業務データ取得権限を付与しない。無効アカウントは拒否。

年度名だけでは開始年／終了年を誤解しやすいため、表示には開始・終了日を付す。10月開始から4月開始へ変更する例：開始済み2025-10〜2026-09は不変、短縮年度2026-10〜2027-03、その次は2027-04〜2028-03。年度境界を明示的に保存し、現在の開始月だけで過去を再計算しない。

**前期間の確認案F**：親要件の「直前にある同じ長さ」を、まず同じ日数で検算する。9/1〜9/30の直前30日は8/2〜8/31。8/21〜8/31の直前11日は8/10〜8/20。2026/3/1〜3/31の直前31日は1/29〜2/28となる。「前月」「前の10日毎区分」とは一致しない。UIに実際の日付範囲を表示する。月次は前暦月、10日毎は前区分という意味を意図していた場合は、この箇所だけ仕様を確認して差し替える。検算では両案を混在させない。

## 4. フィルターと過去時点

- 案件・見込み・売上・請求・入金は関連する案件／売上記録のID集合を先に作り、その後集計する。主担当または共同担当が選択メンバーに一致した案件を一度だけ含める。メンバー別小計同士は重複し得るため、全社合計を小計の足算で作らない。
- 過去の案件状態は期間末Eの変更履歴から復元する。取消・担当変更・無効化が後日行われても、当時の案件数・担当・所属の表示を破壊しない。経費や売上の誤り訂正は別の理由付き訂正／締め版として扱う。
- 事業を選んだ場合：当該事業売上・経費・事業利益を表示し、全社共通費は「全社参考・事業に未配賦」の別枠。全社利益を事業利益と同じカード名で出さない。
- **補足案D**：担当・段階のフィルターは案件関連指標と関連記録へ適用する。経費の支払者を案件担当と同一視せず、月次予算・人件費を担当別や段階別へ按分しない。担当／段階で絞ると対応のない費用・予算・利益カードと予算差は「対象外」、全社参考を表示する場合はフィルター非適用を明示。部分売上から全社経費を引いた値を担当利益として表示しない。
- 支援記録は対象事業／メンバーに明示的に関連した記録を抽出する。案件・活動のリンクは追加参照であり、投稿者がメンバーであることを対象メンバーの代わりに使わない。
- 期間内変化は変化の発生時点の属性を併記する。担当交代・事業変更のイベントは変更前後の選択対象のどちらに一致しても表示する案とし、同イベントIDを一度だけ表示する。

## 6. 手計算で見る代表例

1. **月をまたぐ残高**：8/20売上100,000、8/25請求60,000、9/5入金40,000。9月売上0・請求0・入金40,000。9月末未請求40,000、未入金20,000。9月入金予定60,000があっても実績へ足さない。
2. **成約前後**：9月計上予定100,000の商談中案件は見込み100,000・売上0・着地100,000。成約して予定下書きだけなら見込み0・売上0・着地0。売上計上すると売上100,000・着地100,000。成約時の一時的な着地減少は現行要件どおりで、ここで勝手に成約済予定を足さない。
3. **部分成約**：元案件300,000を成約100,000と継続200,000へ分割。元案件は非アクティブの履歴として残す。成約分の売上確定後は売上100,000・見込み200,000・着地300,000。元案件300,000を重ねて数えない。
4. **未分類経費**：A売上200,000・経費30,000、B売上100,000・経費20,000、共通10,000、人件費80,000、未分類5,000。全社利益155,000。未分類5,000をAへ分類するとA利益は170,000→165,000だが全社利益155,000は不変。
5. **返金と誤入力訂正**：8月の経費10,000を9/5に返金されたら、8月10,000・9月−10,000。入力誤りで実際は8月8,000だった場合は、8月に−2,000の訂正を理由付きで反映し、締め済なら解除・修正・再締め。9月の経費に−2,000を置き換えない。
6. **遅着**：8月締め時点で売上100,000・費用10,000・利益90,000。9/7に8/31利用の経費5,000が届くと、8月の再計算値は利益85,000、状態は再締め待ち。前の締め版90,000も保持する。9月費用には加えない。

## 7. 入力・状態遷移の検証契約

- 一つの売上記録で売上100,000・既請求60,000なら追加請求40,001は拒否。請求60,000・既入金40,000なら追加入金20,001は拒否。他売上の余剰枠で相殺しない。
- 請求予定・入金予定の各合計は売上計上額と一致させる。分割の予定100,000と実績40,000は併存可能で、残額を自動的に実績へしない。
- 成約時：予定なしなら案件額の予定を1件作る。既存予定合計が案件額と一致すれば追加せず、不一致なら拒否。案件金額変更は予定を自動変更せず差を表示する。
- 一括／分割変更は請求・入金実績なし＋確認済みの場合だけ予定を再生成。実績があるときは調整手続きへ。チェック解除も取消と理由を要求する。
- 成約／失注からの再開は理由必須。売上実績付き成約を失注へ変える前に実績の取消・訂正が必要。案件と売上の事業不一致を拒否し、計上後の事業訂正は理由と前後履歴が必要。
- 月次は全社1状態。即時照合未完了／失敗・連携確認待ち・未分類が1件でもあれば締め不可。権限のある経営者だけが締め・理由付き解除を行う。翌月10日超過は注意表示のみで、自動締め・入力停止にしない。
- 通常の編集は締め後禁止。自動連携の遅着は別経路で保存して再締め待ちにする。これを通常編集の自由化とは扱わない。再締め時も即時照合と確認待ち解消が必要。
- 履歴の比較は「今わかっている訂正後の実績」と「当時の締め版」をラベルで区別する。手動の入力誤り訂正を勝手に取消発生日の経済事象へ変えない。

## 8. 検算の範囲と次の作業

`python3 docs/calculation-spec/verify.py` で、JSONの固定期待値を独立した小さな計算処理と照合する。標準ライブラリのみ。実装のコードを呼ばず、認証・DB・Slackの動作がテスト済みとは扱わない。期待値は後続の売上／分割／調整、予算／利益／締め、期間、ダッシュボード、権限の自動テストへ渡す。

仕様の業務確認が終わるまではIssue #5を閉じない。検算済みと業務確認済みを区別する。実装中に差が出たら期待値を実装に合わせて書き換えるのではなく、根拠と変更理由を確認する。
